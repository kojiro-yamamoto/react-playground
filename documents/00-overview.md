## 0-2. React とは何か

React は **UI（画面）を作るための JavaScript ライブラリ**。Meta（旧 Facebook）製。

一言でいうと React の正体はこれ:

```
UI = f(状態)
```

**「今の状態（データ）を渡すと、画面ができあがる」関数**。それが React。
この一行が React のすべてと言ってもいい。以下でこの意味を掘り下げる。

### 従来のやり方（命令的 / imperative）

React を使わない素の JavaScript で「カウンターボタン」を作るとこうなる。

```html
<p id="count">0</p>
<button id="btn">+1</button>

<script>
  let count = 0;
  const countEl = document.getElementById('count');
  const btnEl = document.getElementById('btn');

  btnEl.addEventListener('click', () => {
    count = count + 1;               // ① データを更新して
    countEl.textContent = count;     // ② 画面も自分で更新する ← ここが大変
  });
</script>
```

ポイントは **①データの更新と、②画面の更新を、人間が両方やっている**こと。

これは小さいうちは何ともないが、画面が育つと破綻する。
たとえばタスク管理アプリで「タスクを1件追加する」と、更新すべき箇所は:

- タスク一覧の `<ul>` に `<li>` を1個足す
- 「残り 3 件」のカウンター表示を更新する
- 「タスクがありません」の空メッセージを消す
- 絞り込みが「完了のみ」なら、追加した未完了タスクは**表示しない**

(
<ul> と <li> は、箇条書きのリストを作るためのHTMLタグです。
'''
<ul>
  <li>牛乳を買う</li>
  <li>Reactを勉強する</li>
  <li>部屋を掃除する</li>
</ul>
'''
)

…と、1つの操作に対して画面の更新箇所が芋づる式に増える。
**どれか1つ書き忘れると、データと画面がズレる**。これがバグの温床だった。

### React のやり方（宣言的 / declarative）

React では **画面の更新を人間が書かない**。書くのは「この状態のとき画面はこうなるべき」という**設計図**だけ。

```tsx
function Counter() {
  const [count, setCount] = useState(0);   // ① 状態を宣言

  return (                                  // ② 状態からあるべき画面を宣言
    <>
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
    </>
  );
}
```

`setCount` で状態を変えると、React が**画面を作り直す**。
`countEl.textContent = ...` のような DOM 操作は 1行も書いていない。

| | 命令的（素の JS） | 宣言的（React） |
|---|---|---|
| 書くもの | 画面を**どう変えるか**の手順 | 状態に対する画面の**あるべき姿** |
| 更新箇所 | 人間が全部追跡する | React が差分を計算する |
| 破綻しやすさ | 画面が育つほど危険 | 画面が育っても同じ書き方 |

> **これが React を使う理由。**
> 「画面の更新」という一番ミスしやすい仕事を、人間からライブラリへ移した。

### 「作り直す」のに速いのはなぜか（仮想 DOM）

状態が変わるたびに画面を全部作り直したら遅いのでは？ という疑問が湧くはず。
React は実際の DOM をいきなり触らず、**仮想 DOM（Virtual DOM）**という
軽量な JavaScript オブジェクトの画面コピーを作る。

```
状態が変わる
  → 新しい仮想 DOM を作る
  → 前回の仮想 DOM と比較（差分検出 / diff）
  → 実際に変わった部分だけを本物の DOM に反映
```

「全部作り直す」のは仮想 DOM の世界の話で、
重い実 DOM 操作は必要最小限に絞られる。だから速い。

**当面この仕組みを意識する必要はない**が、「React は差分だけ更新している」と知っておくと、
後で `key` の話（Step 2）が理解しやすくなる。

## 0-3. コンポーネントという考え方

React の 2つ目の柱が**コンポーネント**。

> **コンポーネント = 見た目 + 振る舞いをひとまとめにした、再利用できる UI の部品**

HTML/CSS/JS をファイル種別で分けるのではなく、**「部品」という単位で縦に切る**のが React の発想。

タスク管理アプリを部品に分解するとこうなる:

```
┌─ App ───────────────────────────────┐
│  ┌─ Header ────────────────────┐    │
│  │  タスク管理  残り 2 件        │    │
│  └─────────────────────────────┘    │
│  ┌─ TaskForm ──────────────────┐    │
│  │  [ 入力欄        ] [ 追加 ]  │    │
│  └─────────────────────────────┘    │
│  ┌─ TaskList ──────────────────┐    │
│  │  ┌─ TaskItem ────────────┐  │    │
│  │  │ ☑ 牛乳を買う      🗑 │  │    │
│  │  └───────────────────────┘  │    │
│  │  ┌─ TaskItem ────────────┐  │    │
│  │  │ ☐ 資料を作る      🗑 │  │    │
│  │  └───────────────────────┘  │    │
│  └─────────────────────────────┘    │
└─────────────────────────────────────┘
```

`TaskItem` は 1つ作れば、タスクの数だけ使い回せる。
このアプリは Step を進めながら、まさにこの形へ育てていく。

### コンポーネントの正体はただの関数

身構える必要はない。コンポーネントは**大文字で始まる、JSX を返す関数**でしかない。

```tsx
function Header() {
  return <h1>タスク管理</h1>;
}
```

使うときは HTML タグのように書く。

```tsx
<Header />
```

ルールは 2つだけ:

1. **名前は必ず大文字始まり**（`header` だと HTML の `<header>` タグと区別できない）
2. **JSX を返す**

## 0-4. JSX とは

上のコードで、JavaScript の関数の中に HTML のようなものが直接書かれていた。これが **JSX**。

```tsx
const element = <h1>こんにちは</h1>;   // これは文字列でも HTML でもない
```

**JSX は JavaScript の拡張構文**で、ブラウザはこのままでは読めない。
ビルド時に、ただの JavaScript の関数呼び出しへ変換される。

```tsx
// 書いたコード
<h1 className="title">こんにちは</h1>

// 変換後（イメージ）
React.createElement('h1', { className: 'title' }, 'こんにちは')
```

つまり **JSX は「オブジェクトを作る式」の見た目を良くした糖衣構文**。
だから JSX は変数に入れられるし、関数の引数にも戻り値にもできる。

### JSX のルール（HTML との違い）

初心者が必ず一度は踏む地雷。ここにまとめておく。

**① `class` ではなく `className`**

`class` は JavaScript の予約語なので使えない。

```tsx
<div className="card">…</div>
```

**② 属性はキャメルケース**

```tsx
<input onChange={...} maxLength={10} />   {/* onchange, maxlength ではない */}
```

**③ タグは必ず閉じる**

```tsx
<br />   <img src="..." />   <input />   {/* 単独タグもスラッシュが必要 */}
```

**④ 返せる要素はひとつだけ**

関数は値を1つしか返せないので、JSX も1つのルート要素にまとめる必要がある。

```tsx
// ✗ エラー
return (
  <h1>タイトル</h1>
  <p>本文</p>
);

// ○ 余計な <div> を増やしたくないときは「フラグメント」<> </> で包む
return (
  <>
    <h1>タイトル</h1>
    <p>本文</p>
  </>
);
```

**⑤ `{ }` の中には JavaScript の「式」を書ける**

JSX の最重要ポイント。中括弧で JavaScript の世界に戻れる。

```tsx
const name = '山本';
const tasks = ['牛乳を買う', '資料を作る'];

return (
  <div>
    <p>こんにちは、{name}さん</p>              {/* 変数 */}
    <p>残り {tasks.length} 件</p>              {/* 式 */}
    <p>{tasks.length === 0 ? '完了！' : '未完了あり'}</p>  {/* 三項演算子 */}
  </div>
);
```

書けるのは **式（値になるもの）**だけ。`if` 文や `for` 文といった**文は書けない**。
条件分岐は三項演算子 `? :`、繰り返しは `map()` を使う（Step 2 で扱う）。

**⑥ コメントは `{/* */}`**

```tsx
{/* JSX 内のコメントはこう書く */}
```

## 0-5. なぜ Vite が必要なのか

ここまでで分かる通り、`.tsx` ファイルは**ブラウザがそのまま読めない**。

- JSX（`<h1>…</h1>`）→ ブラウザは知らない構文
- TypeScript の型注釈 → ブラウザは知らない構文
- `import` によるファイル分割 → まとめる作業が要る

これらを**ブラウザが読める普通の JavaScript へ変換する**のがビルドツールの仕事。
その現代的な定番が **Vite（ヴィート、フランス語で「速い」）**。

Vite が提供するもの:

| 機能 | 内容 |
|---|---|
| 開発サーバー | `npm run dev` で `localhost:5173` を起動 |
| 変換 | `.tsx` → ブラウザが読める JS へ |
| **HMR** | ファイルを保存した瞬間、リロードなしで画面へ反映（Hot Module Replacement） |
| 本番ビルド | `npm run build` で配信用に最適化・圧縮 |

**HMR は開発体験の中心**。コードを保存 → 即座にブラウザが変わる、というリズムで開発する。

## 0-6. なぜ TypeScript を使うのか

TypeScript は **JavaScript に「型」を足した言語**。`.ts` / `.tsx` がその拡張子。

```ts
// JavaScript: 何が入るか誰にも分からない
let count = 0;
count = "3";        // 通ってしまう。実行時に謎のバグへ

// TypeScript: 宣言した型を守らせる
let count: number = 0;
count = "3";        // ✗ エディタが即座に赤線で警告
```

React では特に、**コンポーネント間で受け渡すデータの形**を型で明示できるのが効く。

```ts
type Task = {
  id: string;
  title: string;
  done: boolean;
};
```

こう書いておくと、`task.titel` とタイポした瞬間にエディタが教えてくれるし、
`task.` と打つだけで候補（`id` / `title` / `done`）が出る。
**型は「書く手間」ではなく「エディタからの支援」**と捉えるとよい。

## 0-7. ファイル構成と、起動の流れ

```
react-playground/
├── documents/          ← 学習ノート（このファイルたち）
├── public/             ← 画像などをそのまま配信するフォルダ
├── src/                ← ★ アプリのソースコード。作業はほぼここ
│   ├── main.tsx        ← React の起動地点
│   ├── App.tsx         ← アプリ本体のコンポーネント
│   ├── index.css       ← 全体に効く CSS
│   └── App.css         ← App 用の CSS
├── index.html          ← 唯一の HTML
├── package.json        ← 依存ライブラリとコマンドの定義
├── vite.config.ts      ← Vite の設定
├── tsconfig*.json      ← TypeScript の設定
└── node_modules/       ← DL されたライブラリ本体（Git 管理外）
```

### 画面が表示されるまで

React アプリは **「HTML は1枚だけ、中身は全部 JavaScript が描く」**という作り
（SPA = Single Page Application）。その流れが次の3ファイルに現れている。

**① `index.html`** — 中身はほぼ空。React が描き込む「器」を用意するだけ。

```html
<div id="root"></div>                          <!-- ここに React が描画する -->
<script type="module" src="/src/main.tsx"></script>
```

**② `src/main.tsx`** — 起動地点。「`root` という器に `App` を描いて」と命令する。

```tsx
createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <App />
  </StrictMode>,
)
```

**③ `src/App.tsx`** — アプリ本体。ここから先を育てていく。

```
index.html の <div id="root">
      ↑ ここに描画せよ、と指示
main.tsx  ──renders──▶  App.tsx  ──▶  Header / TaskForm / TaskList …
```

### `main.tsx` の細かい部分

初見で気になる 2つに触れておく。

**`<StrictMode>`**
開発時だけ有効になる「厳格モード」。危険な書き方を検出するため、
**あえてコンポーネントを2回実行する**。そのため `console.log` が2回出ることがあるが、
バグではない。本番ビルドでは1回になる。

**`getElementById('root')!` の `!`**
TypeScript に「これは絶対 `null` じゃない」と伝える記号（非 null アサーション）。
`getElementById` は「要素が見つからない可能性」があるため戻り値が `null` を含むが、
`index.html` に確実に書いてあるので、開発者が保証している。

## 0-9. これから学ぶことの地図

React の学習範囲は広く見えるが、**中心にあるのは「状態（state）」ひとつ**。
残りはその周辺装備、と捉えると全体像が掴める。

```
                   ┌─────────────┐
                   │   状態 state │  ← React の中心。これが変わると画面が変わる
                   └──────┬──────┘
          ┌───────────────┼────────────────┐
          │               │                │
    ┌─────▼─────┐  ┌──────▼──────┐  ┌──────▼──────┐
    │  useState │  │    props    │  │  useEffect  │
    │ 状態を持つ │  │ 状態を子へ渡す│  │ 外の世界と繋ぐ│
    └───────────┘  └─────────────┘  └─────────────┘
       Step 3          Step 2            Step 7
```

| Step | テーマ | 学ぶ中心概念 |
|---|---|---|
| 0 | 全体像とプロジェクト構成 | React の思想、JSX、コンポーネント |
| 1 | 画面の骨組みを作る | JSX で UI を組む、CSS の当て方 |
| 2 | タスク一覧を表示する | 配列の `map`、`key`、`props`、型定義 |
| 3 | 完了 / 未完了を切り替える | `useState`、再レンダリング、イミュータブル更新 |
| 4 | タスクを追加する | フォーム、制御コンポーネント、イベント |
| 5 | タスクを削除する | `filter`、state の持ち上げ |
| 6 | 未完了だけ表示する絞り込み | 派生した値、state を増やしすぎない設計 |
| 7 | リロードしても消えないようにする | `useEffect`、副作用、localStorage |
| 8 | ファイルを分割して整理する | コンポーネント設計、型の置き場所 |

## 0-10. 用語集

| 用語 | 意味 |
|---|---|
| **コンポーネント** | JSX を返す関数。UI の部品。名前は大文字始まり |
| **JSX** | JS の中に HTML 風の記述を書ける拡張構文。ビルド時に JS へ変換される |
| **props** | 親から子コンポーネントへ渡すデータ。読み取り専用 |
| **state（状態）** | コンポーネントが持つ、変化するデータ。変わると画面が再描画される |
| **レンダリング** | コンポーネント関数を実行して、画面のあるべき姿を求めること |
| **再レンダリング** | 状態が変わって、もう一度レンダリングが走ること |
| **仮想 DOM** | React が内部に持つ画面のコピー。差分計算に使う |
| **フック（Hook）** | `use` で始まる React の関数群。`useState` / `useEffect` など |
| **SPA** | Single Page Application。HTML 1枚で画面遷移まで JS がこなす作り |
| **HMR** | Hot Module Replacement。保存した瞬間、リロードなしで画面へ反映される仕組み |

## この Step のまとめ

- React は **`UI = f(状態)`**。状態を宣言すれば、画面の更新は React がやる
- 画面は**コンポーネント**（JSX を返す大文字始まりの関数）という部品に分けて組み立てる
- **JSX** は JS の拡張構文。`className` / キャメルケース / タグを閉じる / ルートは1つ / `{}` で JS書ける
- `.tsx` はブラウザが読めないので、**Vite** が変換し、開発サーバーと HMR を提供する
- **TypeScript** の型は制約ではなく、エディタからの支援
